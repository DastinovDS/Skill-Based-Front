# Protocol message fixtures

Typical WebSocket messages of the match protocol (PRO-01, #44). They are used by the client tests
(the fake server CLI-01, #57; the snapshot buffer CLI-02, #58) and the protocol tests in Python.

The source of truth about the schema: the Pydantic models of `gow_protocol` (`packages/protocol/src/gow_protocol/`).
The fixtures are written by hand, not generated by code. The test `packages/protocol/tests/test_messages.py`
checks that every fixture passes validation and gives the same JSON after `decode` → `encode`,
that there is a fixture for at least every message type and every command type, and that the file name
starts with the message type (`command_<command type>` for commands).

The client test `apps/client/src/protocol.test.ts` checks that every fixture passes the type check
against the generated `ClientMsg` and `ServerMsg` (`apps/client/src/protocol.gen.ts`, PRO-02, #45).

If you changed the schema: raise `PROTOCOL_VERSION` (`gow_protocol.messages`), fix the fixtures and
`hello.json` (`protocol_version`).

## Layout

| Directory | What | Decoder |
|---|---|---|
| `client/` | client → server: `hello`, `command` (every command type: SIM-04 #20 and later, the economy v2 ones of DEC-41 #647 among them), `ping`, `resync`, `pause`, `resume`, `reach_query` (DEC-20) | `gow_protocol.codec.decode_client` |
| `server/` | server → client: `welcome`, `snapshot`, `ack`, `event`, `match_end`, `error`, `pong`, `paused`, `reach` (DEC-20) | `gow_protocol.codec.decode_server` |

## How the messages are built

- Every message: an object with the field `type`; a command is inside `command.cmd`: an object with its own `type`.
- An extra field, a missing field, a fractional number, `true` instead of a number, a string instead of a number: an error.
  All game quantities are integers, as in the simulation: CP in hundredths, `progress` in thousandths of an edge, time in ticks.
- Nodes and edges are named by the map ids (the map is public). Own groups, packets and intents: opaque
  string ids of the player (`[A-Za-z0-9_-]{1,32}`), there are no sequential simulation ids on the wire.
- The view (`snapshot.view`) has only own groups and packets. About the opponent only what
  DEC-04 (#10) allows is known: the `seen` summary of a node or an edge (modes; sums of units and charges only
  at `exact`), the public ownership, capacity, VP and intents (without the group id and size).
- `nodes[i].id == i` and `edges[i].id == i`: the view always has all the nodes and edges of the map.
