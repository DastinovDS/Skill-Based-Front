# Фикстуры сообщений протокола

Типовые сообщения WebSocket-протокола матча (PRO-01, #44). Ими пользуются тесты клиента
(фейковый сервер CLI-01, #57; буфер снапшотов CLI-02, #58) и тесты протокола на Python.

Источник правды о схеме: Pydantic-модели `gow_protocol` (`packages/protocol/src/gow_protocol/`).
Фикстуры написаны вручную, а не сгенерированы кодом. Тест `packages/protocol/tests/test_messages.py`
проверяет, что каждая фикстура проходит валидацию и после `decode` → `encode` даёт тот же JSON,
что есть фикстура хотя бы на каждый тип сообщения и каждый тип команды и что имя файла
начинается с типа сообщения (`command_<тип команды>` для команд).

Тест клиента `apps/client/src/protocol.test.ts` проверяет, что каждая фикстура проходит проверку
типов против сгенерированных `ClientMsg` и `ServerMsg` (`apps/client/src/protocol.gen.ts`, PRO-02, #45).

Изменил схему: повысь `PROTOCOL_VERSION` (`gow_protocol.messages`), поправь фикстуры и
`hello.json` (`protocol_version`).

## Раскладка

| Каталог | Что | Декодер |
|---|---|---|
| `client/` | клиент → сервер: `hello`, `command` (все девять команд SIM-04, #20), `ping`, `resync` | `gow_protocol.codec.decode_client` |
| `server/` | сервер → клиент: `welcome`, `snapshot`, `ack`, `event`, `match_end`, `error`, `pong` | `gow_protocol.codec.decode_server` |

## Сценарии

- `server/welcome.json`: игрок 0 на карте `diamond` (`packages/sim/tests/maps/diamond.json`),
  `ruleset_public` с числами `rulesets/mvp-0.toml` на момент написания (рулсет может уйти вперёд,
  фикстура от этого не ломается).
- `server/snapshot.json`: вид игрока 0 на `diamond`, тик 120. Узлы 0 и 1 свои (`exact`), узлы 2 и 3
  соседние (`presence`, у столицы противника видны режимы `attack` и `defense` без чисел),
  ребро 2 в тумане с памятью с тика 60, по ребру 3 идёт вражеская группа (только режим).
  Три свои группы (одна на ребре с приказом), свой пакет, два намерения: своя «Защита» и
  запланированный приказ противника 3 → 1.
- `server/snapshot_fog.json`: вид игрока 0 на `line3`, тик 300. Столица противника в тумане с памятью
  с тика 90, ребро 1 в тумане и ни разу не виденное (`seen: null`), город 1 захвачен противником.
- `server/snapshot_clash.json`: вид игрока 0 на `siege`, тик 400, насыщенная сцена для проверки отрисовки клиента
  (CLI-04, #60): три группы в одном городе (одна из 12 юнитов), две группы на дорогах с приказами, два пакета,
  противник с точными числами в нейтральном городе, присутствие противника с несколькими режимами,
  намерения обеих сторон (запланированные приказы, «Защита», стройка), город в тумане с памятью.
- `server/ack_move.json`, `ack_ok.json`, `ack_reject.json`: принятый `move` с путём, принятая команда
  без пути, отказ `NOT_ENOUGH_CP`.
- `server/event.json`: пример события. Набор событий (`kind` и поля `data`) задают системы
  симуляции (SIM-06…SIM-13), фильтрацию по видимости делает PRO-03 (#46).
- `server/match_end.json` (захват столицы), `match_end_draw.json` (ничья по таймеру).

Токен в `client/hello.json` ненастоящий.

## Как устроены сообщения

- Каждое сообщение: объект с полем `type`; команда внутри `command.cmd`: объект со своим `type`.
- Лишнее поле, пропущенное поле, дробное число, `true` вместо числа, строка вместо числа: ошибка.
  Все игровые величины целые, как в симуляции: CP в сотых, `progress` в тысячных ребра, время в тиках.
- Узлы и рёбра называются id карты (карта публична). Свои группы, пакеты и намерения: непрозрачные
  строковые id игрока (`[A-Za-z0-9_-]{1,32}`), последовательных id симуляции на проводе нет.
- В виде (`snapshot.view`) только свои группы и пакеты. Про противника известно только то, что
  разрешает DEC-04 (#10): сводка `seen` по узлу или ребру (режимы; суммы юнитов и зарядов только
  при `exact`), публичные владение, ёмкость, ширины дорог, VP и намерения (без id и размера группы).
- `nodes[i].id == i` и `edges[i].id == i`: в виде всегда все узлы и рёбра карты.
