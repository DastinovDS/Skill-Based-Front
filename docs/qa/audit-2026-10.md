### CLI-01: the match WebSocket reconnects forever on terminal close codes (medium, #416)

`matchConnection.ts:269-289` (`#onClose`): every close code except 4001 and 4009 schedules another
attempt, without a limit. The server answers 4004 for an unknown token, an unknown or finished
match and a non-participant (`ws.py`), and 1008 for policy and rate limit; a refused `Origin` is
rejected before accept (the browser sees 1006). After the 60 s window of DEC-05 the match of a
sleeping laptop is over, or the server restarted, or the account logged in elsewhere (new token):
the client then retries every 12 to 15 s indefinitely behind the banner "Connection lost.
Reconnecting..." (`LiveMatch.svelte:242`), the banner has no button, and the forfeit command of
the exit dialog is queued behind a connection that never opens. The result screen and the replay
link are never shown. A page reload goes back to the menu.

Evidence: reproduced on the production build: the server killed and started again during a bot
match; sockets `1006` x5, then `4004:no such match` at t+59 s, t+71 s, t+86 s, banner unchanged.
Fix: treat 4004 as terminal after one or two retries with a status `gone` ("the match is over",
"To menu"); cap attempts for the rest and offer a manual retry; cap the unacknowledged-command
queue (a resend burst over the token bucket of 60 closes with 1008 each time); an exit button in
the reconnecting banner. Effort S. Protocol and server: no.

### CLI-02: no liveness watchdog on the match WebSocket (medium, #417)

`matchConnection.ts:254-266` sends a `ping` every 5 s; the `pong` (`:219`) only feeds the RTT.
Nothing notices silence. If the link dies without a FIN or RST (Wi-Fi change, sleep and wake, NAT
timeout) the browser raises `close` only when its own TCP timeout expires, while the server hits its
send timeout, marks the player disconnected and queues `Forfeit` after `GOW_RECONNECT_WINDOW_S`
(60 s). The client never tried to reconnect. `online` and `visibilitychange` are not used either.
Evidence: code reading. The browser detection time is an assumption: settle it with the Network Link
Conditioner (drop the link, count the seconds until `onclose`). Fix: record the time of the last
frame (snapshots come at 10 Hz); no frame for about 3 s while `ready`, or two unanswered pings,
means close and reconnect; reconnect at once on `online` and when the tab becomes visible. Effort S.
Protocol and server: no.

### CLI-03: one exception in a render frame stops the map for good (medium, #418)

`mapScene.ts:148,253`: `onFrame` is a PixiJS ticker listener without a `try/catch`. In PixiJS
8.21 (`lib/ticker/Ticker.mjs:123-130`) the next animation frame is requested only after the
listeners return, so a listener that throws ends the loop permanently. The canvas freezes on the
last frame while the HUD (separate state, same snapshots) goes on, and `GameCanvas.onerror` fires
only for a failed `init`, so there is no notice either. There is no `<svelte:boundary>` and no
`error` / `unhandledrejection` handler anywhere in `src`. What feeds the loop: `decode.ts:53-65`
checks shapes shallowly (ids, counters, `detail`, `me.cp`) while the render code dereferences far
more, `welcome.ruleset_public` is only checked to be an object, and the server validates snapshots
outside prod only (`validate_snapshots=env != "prod"`, `security-audit.md` 3.2).
Evidence: a scratch Vitest test with the real `Ticker` and a fake `requestAnimationFrame`: a
listener that throws on its second call is never called again (2 calls in 6 frames); not
committed. That a real snapshot can make `onFrame` throw today is a hypothesis; the finding is that
any such bug is permanent and silent. Fix: `try/catch` in `onFrame` that logs once, skips the frame
and, after repeated failures, shows the renderer-failed overlay with "Reload"; a boundary around
the match and replay views; one global error logger without tokens. Effort S to M.

### CLI-04: the fog veil dims own figures on edges (medium, #419)

The known gap of DEC-10 (#403). `fogLayout.ts:85` (`veilCities`) and `fogView.ts:309-322`
(`setRegions`) build the veil from the node `detail` only and fill the whole Voronoi cell of every
hidden city (`FOG_VEIL`: alpha 0.66); `layers.ts:13-14` puts `fog` above `groups`. Since DEC-10 an
own group on a road sees its own edge, so the visible half of that road, lying in the cell of the
hidden end node, and the group (and any visible enemy figure) on it are darkened exactly while the
player steers an army into the fog. No leak: only own or visible things are dimmed. Evidence: code
and layer order; no screenshot (the dev scenes have no fixture for it, add one with the fix).
Fix: smallest, draw `groups` above `fog` (the server sends enemy figures only when visible; the
memory ghosts live in the fog layer itself); proper, cut the visible edge halves out of the veil and
rebuild the cache when that set changes; add a fog test and a dev scene. Effort S (layer) to M
(corridor). Touches the render files of #347 (merged).

### CLI-05: the production bundle carries test maps, fixtures and backgrounds (low)

`map/bundledMaps.ts` is imported by `LiveMatch.svelte` and `ReplayViewer.svelte` only for
`backgroundUrl(map.meta.name)`, but its two eager `import.meta.glob`s pull every map JSON of
`maps/`, `maps/fixtures/` and `packages/sim/tests/maps/` into the main chunk (15 maps, about 85 kB
of 510 kB) and every `*.bg.webp` into `dist/assets` (2.2 MB, 6 files, 3 of them for maps that are not in
the server pool). The server already gives `MapSummary.background_url` and serves
`/api/maps/{id}/background.webp`; the client uses neither. So the map comes from the server but its
picture from the bundle by name: two sources of truth, and the client build depends on `maps/` and
the simulation's test files (AGENTS.md section 2 allows the client only `protocol.gen.ts` and
`api.gen.ts`; see the COPY lines in `deploy/caddy.Dockerfile`). Answer to the SRV note: the dev screen
itself is not reachable in the production build (`import.meta.env.DEV` gates the dynamic import;
`dist/` has no `DevScreen`, scenario, fixture or `rusher` strings), only the data above is. Fix: load
the background from the server URL, keep `bundledMaps` dev-only (dynamic import under `DEV`). Effort S.

### CLI-09: no automated check of run-time CSP violations (low)

The CSP header is compared with `csp.ts` (`check-caddy.sh`, `csp.test.ts`), but nothing runs the
application under it and fails on a violation: the e2e specs listen to `pageerror` only
(`e2e/tests/bot-and-pages.spec.ts:21,51`), and a violation is a console message and a

and two bot matches with the Pixi canvas (the second one for 8 minutes): 0 `securitypolicyviolation`
events in the first, no CSP message in the console of either. Fix: in the e2e
fixture collect `securitypolicyviolation` (`page.addInitScript`) and `console` errors and assert
none at the end of each spec. Effort S.

### CLI-10: a match offer can go unnoticed in a background tab (low)

`QueueScreen.svelte` polls every 1 s with `setInterval`; the place is dropped after `stale_s` = 15 s
without a poll (`matchqueue.py`), and a found pair has `confirm_s` = 15 s. Chrome clamps background
timers to 1 per minute after about 5 minutes hidden, so a player who tabs away while waiting for a
rated opponent is dropped silently and, when still in, has no sound, title change or notification
for the 15 s to confirm. Polls of `InviteScreen` (1.5 s) and `LobbyScreen` are `setInterval` too
and overlap when the server is slow. Hypothesis; for a playtest with few players the queue waits are
long, so this will be met. Fix: flash `document.title` and play the sound on a found pair, poll with
a timeout and no overlap, tell the player in the queue that the tab must stay open. Effort S.

### CLI-11: a stale tab wipes the newer token (low)

`appState.svelte.ts:103,278` calls `forgetGuest(storage)` on a 401, which removes `sbf.guest`
whatever it holds. Log in (or change the password) in tab B: the token in storage is the new one
and the one of tab A is dead; the first call of tab A gets 401 and deletes tab B's token, so the
next reload of any tab starts at the welcome screen. There is no `storage` event handler either.
For an account with a password this costs a login; a guest who set a password in another tab
only. Fix: remove the entry only if it still holds the token that failed; listen to `storage`.
Effort S.

### SRV-01: HTTP request bodies are not size-limited (high, #411, details withheld)

- **Severity**: high: anonymous, no account and no preparation, and it hits the single process that
  runs every match (AGENTS.md, 5.1).
- **Location**: `apps/server/src/gow_server/app.py` (no body limit in the app),
  `deploy/Caddyfile:39-42` (`/api/*` proxied without `request_body` limits), `compose.yaml` (`app`
  has no memory limit). Every endpoint with a JSON body, the unauthenticated `POST /api/guest` and
  `POST /api/login` included.
- **Impact**: FastAPI reads the whole body into memory and decodes the JSON on the event loop before
  the endpoint and its rate limit run. Large bodies cost a multiple of their size in memory and stall
  the tick loop of every match while they are parsed; enough of them exhaust the memory of the VPS,
  and the restart aborts every running match.
- **Evidence**: checked through Caddy on the agent stack (measurements with the owner);
  `apps/server/tests/test_audit_srv.py::test_oversized_body_is_refused_before_parsing`
  (`xfail(strict=True)`: today 422 after a full read, expected 413).
- **Fix**: an ASGI middleware that answers 413 over a small limit (16-64 KiB; real bodies are a few
  hundred bytes) by `Content-Length` and by counting streamed bytes; `request_body { max_size }` on
  `/api/*` in Caddy; a memory limit for `app`.
- **Effort**: S. Protocol: no. DB schema: no.

### SRV-02: no global cap on running matches (medium, #412)

- **Severity**: medium: needs many accounts, then degrades every match on the server.
- **Location**: `apps/server/src/gow_server/matches.py:667` (`MatchManager.create`),
  `apps/server/src/gow_server/botmatch.py:61`, `apps/server/src/gow_server/matches.py:426-432` (the
  reconnect window runs before the first connection, DEC-05).
- **Scenario**: the only limits are per player (one active match; 10 created per 10 minutes). A bot
  match starts at once and runs without a WebSocket until the 60 s window forfeits it, then the next
  one can be created: every guest account keeps about one match running (ticks, bot decisions, a
  replay log, a frames build in the worker) with plain HTTP calls. Guests cost nothing (10 per hour
  per IP, see SRV-05) and never expire. Past 30 matches per core (AGENTS.md, 12) the tick lag of all
  real matches grows. A connected attacker adds up to 20 `resync` per second per connection
  (0.4 ms each, measured on `crossroads`), a minor amplifier.
- **Evidence**: code path; the capacity figure is the budget of AGENTS.md 12, not a load test here
  (#85).
- **Fix**: a global cap of running matches (lower for bot matches) from settings, 503 when full, a
  metric and an alert; abort a bot match without a WebSocket after 10-15 s as never started (no
  replay, no frames); optionally bot matches only for password accounts or a per-IP cap.
- **Effort**: M. Protocol: no. DB schema: no.

### SRV-03: unbounded concurrent scrypt on anonymous login (medium, #413)

- **Severity**: medium: anonymous and instant, but the worst case needs two or more addresses and
  the effect is transient.
- **Location**: `apps/server/src/gow_server/identity.py:215-244` (`login`), `:189-212`
  (`set_password`), `apps/server/src/gow_server/passwords.py:36-45`.
- **Scenario**: every login runs one scrypt (N=2^15, r=8: 32 MiB, about 0.1 s of CPU; 93 ms on the
  audit machine), also for an unknown nick (by design, against nick probing). Concurrency is bounded
  only by the FastAPI threadpool (40 threads); the limits count requests per window (20 per IP, 10
  per nick per 10 minutes), not hashes in flight. During the hash the request holds a pooled DB
  connection (`QueuePool` 5 + 10 overflow, timeout 30 s), so a burst also delays match-start inserts,
  result writes (`lifecycle._write_result`) and WebSocket token lookups. `hashlib.scrypt` releases
  the GIL (checked: the main thread kept ticking), so the cost is memory, CPU and the pool, not a
  frozen event loop.
- **Evidence**: on the agent stack, 10 concurrent anonymous logins raised the `app` memory peak from
  78 MiB to 390 MiB (`/sys/fs/cgroup/memory.peak`; the per-nick limit cut the other 10 to 429).
  40 hashes at once would be about 1.3 GiB on a 2 GB VPS.
- **Fix**: a semaphore around scrypt (2-4), answer 429/503 at once over it; verify outside the
  transaction (read the hash, release the connection, hash, write the token); consider
  `GOW_SCRYPT_N=2^14` after measuring on the VPS (needs SRV-07 to take effect); a memory limit for `app`.
- **Effort**: S. Protocol: no. DB schema: no.

### SRV-04: rated ladder boosting with throwaway accounts (medium, #414)

- **Severity**: medium: breaks the integrity of the rated ladder with little effort; the fix is a
  rules decision of the owner (DEC-06: a forfeit and a no-show are a full defeat).
- **Location**: `apps/server/src/gow_server/matchqueue.py:358-441` (a guest without a password may
  queue for a rated match), `apps/server/src/gow_server/lifecycle.py:362-370` and
  `apps/server/src/gow_server/rating.py:153` (a forfeit or no-show at tick 1 is rated like a full
  match), `apps/server/src/gow_server/matchqueue.py:245-282` (the opponent's nick is shown before
  both confirm).
- **Scenario**: win trading: a player queues together with a fresh guest of their own; with a small
  queue they are paired and the alt forfeits or never connects. "Never the same pair twice in a row"
  does not stop a new alt each time. Related: dodging, since the found opponent's nick is visible
  before confirming and declining costs only a re-join (20 per minute).
- **Evidence**: code path and `gow_server.rating` arithmetic: 10 wins against fresh accounts
  (`rate_match(m, Glicko(), WIN)`) move the displayed rating `r - 2 RD` from 800 to 1643, 20 wins to
  1803 (`r` 2100, so the 400-point queue window still pairs it with new accounts for the first wins).
  Not run end to end.
- **Options**: rated queue only for password accounts, optionally with a minimum account age or a
  few unrated matches; no gain for the winner of a match that ended by forfeit or no-show before N
  ticks (the loser still loses, so it is no escape); a daily cap of rated matches against the same
  opponent; no pairing of two accounts from the same address in one pass (in memory, like the
  limits); hide the nick until both confirmed.
- **Effort**: M. Protocol: no (the queue is HTTP; hiding the nick changes `api.gen.ts`). DB schema: no.

### SRV-05: per-IP limits keyed by the exact address (medium, #415)

- **Severity**: medium: every per-IP limit depends on it (guests, logins) and it amplifies SRV-02,
  SRV-03 and SRV-04. The second part is a hypothesis.
- **Location**: `apps/server/src/gow_server/identity.py:255-258` (`_client_ip`), `compose.yaml:72-75`.
- **Scenario**: (1) an IPv6 client controls a /64: each address is a new key, so the guest limit
  (10 per hour per IP) and the login limit per IP do not hold. (2) Hypothesis: when the Docker
  network of Caddy has no IPv6, Docker's userland proxy answers IPv6 connections on `[::]:443`
  (the stack publishes there: `[::]:8443->443/tcp` in `docker ps`) and connects to the container over
  IPv4, so every IPv6 client may reach Caddy from the bridge gateway address: all IPv6 players share
  one key, and one of them can exhaust guest creation and logins for the others. Not checked on the
  VPS; Docker Desktop on macOS is not representative.
- **Fix**: key IPv6 by its /64; on the VPS check the address the server sees for `curl -6`, then
  enable IPv6 on the `edge` network or disable the userland proxy, or publish no AAAA record until
  checked; document it in `docs/ops/deploy.md`, section 8.
- **Effort**: S. Protocol: no. DB schema: no.

### SRV-06: anyone can lock an account's password login (low)

- **Severity**: low: denies password login on a new device only; the current device keeps its token.
- **Location**: `apps/server/src/gow_server/identity.py:225-231`, `apps/server/src/gow_server/abuse.py:37`.

  alert) against distributed guessing.
- **Effort**: S. Protocol: no. DB schema: no.

### SIM-01: `Move` and `Merge` in one tick bypass the stack limit (medium, #435)

- **Severity**: medium: a modified client breaks an accepted rule (DEC-20, D) every time it wants,
  undetected by the server; the gain is limited because two groups can travel the same path anyway.
- **Location**: `packages/sim/src/gow_sim/commands.py:476-489` (`Merge` validation: only
  `_standing_group`, which accepts a group with a fresh, not planned move order),
  `commands.py:797-803` and `systems/orders.py:71-81` (`absorb`: the kept group keeps its order),
  `commands.py:450-466` (`Move` checks the stack limit with the size at the command).
- **Scenario**: in one tick a player sends `Move(g1, dest)` for a group that fits every node of the
  path, then `Merge(g1, g2, ...)` with `g1` the smallest id (a split makes that easy). Both are
  applied at the start of the tick, before `movement`: `g1` still stands (`AtNode`, a plain order
  does not wait), so the merge is accepted, `g1` keeps its order and leaves with the merged size.
  DEC-20, D3 says the check is once, at the command, because "the size of the group on the way does
  not change"; here it does. The player moves an army of any size through and into nodes the
  limit closes to it (A5: such a group should leave only after a split), with one `move` paid
  instead of one per group. Repeatable: split, then `Move` and `Merge` again the next tick.
- **Evidence**: reproduced on the `dec20` map of `test_dec20.py` (capacity of B is 4): an 8-unit
  group gets `STACK_LIMIT` for `Move(B)`; `Move(g1 of 4, B)` plus `Merge(g1, g2 of 4)` in one tick
  are both `Ok`, and the 8-unit group stands in B at tick 25 (script under "How to repeat").
- **Fix**: reject `Merge` when a group holds a move order (`GROUP_BUSY`, as for a waiting planned
  order), or drop the order of the merged group; either keeps D3 true. A check of the stack limit
  at departure would also work but adds a rule. Effort S. Rules: no new rule, D3 is enforced;
  replays with such a pair would change, so `SIM_VERSION` and golden replays; protocol: no.

### Checked and found sound

- Fog: `project()` is the only exit; enemy groups appear only as `seen` totals by the level of the
  place, figures on edges in sight (DEC-33) and fight totals; nothing about enemy CP, stance,
  production, barracks (except DEC-31), warehouse levels, builds in fog or recruit queues. `reach`
  answers `None` alike for unknown, foreign and moving groups. Reject codes that read enemy state
  read only public data (owners, capacities, fights).
- Opaque ids: keyed blake2b with a per-match `secrets.token_bytes` key, separate personalizations
  for own entities and enemy figures, 63 bits, sorted by opaque id; never reused (the id counter
  only grows), so a stale id is `NOT_FOUND_OR_HIDDEN`. The key is in the replay log header, which
  is never served. `HEADLESS_MATCH_KEY` is used only by `run_headless`.
- Validation: every node, edge, marker and count is range-checked before use; `Split`, `Transfer`,
  `SetRearMin`, `SetFront` reject out-of-range values; a rejected command changes nothing; the
  wire limits integers to int32 and `merge.groups` to 16; `seq` is strictly increasing on the
  server, so the duplicate check of `apply_commands` cannot fire from the wire.
- Determinism: no `set`, `hash()`, `float`, `random`, `time` or I/O in the step path (`analysis.py`
  uses `float` for reports only); every iteration is sorted; rulesets reject floats and booleans
  as numbers; `test_determinism.py` and `test_symmetry.py` pass.
- Player symmetry: commands of one player read only its own entities, public data and the enemy
  visibility fixed at the start of the tick; tie-breaks are by `node_key` or within one player.
- Protocol: every model is `extra="forbid"`, `strict`, `hide_input_in_errors`, `frozen`; the
  adapters set `hide_input_in_errors` too; opaque ids that are not canonical 63-bit decimals become
  unknown ids, never an exception.
- Bots: decide on `match.view(slot)` only, opaque-id commands go through `resolve()`, an exception
  in a bot is logged and skipped; parameters come from the match seed.
- Replays: header with `sim_version`, `ruleset_hash`, `map_hash`, `match_key`; the archived
  ruleset is checked against its hash; another `SIM_VERSION` raises.
- Performance with a split army: in progress.

### Notes for the other areas

- SRV: the bot overrun skip (`matches.py`, `_bot_skip_next`) depends on wall-clock time, so a bot
  match is not reproducible from its seed; the replay log records the commands, so replays are not
  affected. A `reach_query` costs two path searches; the token bucket bounds it.
- CLI: SIM-07 answers the `decode.ts` question; SIM-05 lists the `ruleset_public` fields the client
  never reads.
