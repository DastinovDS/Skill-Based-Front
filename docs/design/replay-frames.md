# Формат файла кадров реплея

Файл кадров (SRV-07, #54): полное состояние матча дважды в секунду плюс все события. Просмотр
(CLI-10, #66) читает только его: пересимуляция в браузере не нужна, и файл не ломается при смене
`SIM_VERSION` или рулсета. Файл показывает **настоящее состояние обоих игроков без тумана войны**:
сервер отдаёт его только после матча.

Код: `gow_server.frames` (`build_frames`, `FORMAT`). Версия формата: поле `format` (сейчас `1`);
клиент обязан отказаться от файла с неизвестным `format`.

## Откуда берётся

Во время матча сервер пишет журнал команд `data/replays/{id}.jsonl.gz` (`gow_sim.replay`,
`AGENTS.md` 4.5). После матча он пересимулирует журнал в `ProcessPoolExecutor` (не в цикле событий и
не в потоке), сверяет хэш состояния на каждой контрольной точке журнала и пишет
`data/replays/{id}.frames.json.gz`. Хэш не сошёлся или матч не доигран: файл не создаётся, журнал
остаётся для разбора. В `matches.replay_path` лежит имя файла кадров относительно `data/replays/`.
Журнал не отдаётся наружу: в его заголовке секрет `match_key`.

`GET /api/replays/{id}` (`id` = `matches.id`) отдаёт файл как есть (`Content-Type:
application/json`, `Content-Encoding: gzip`): браузер распаковывает сам, `fetch(url).then(r =>
r.json())` работает без библиотек. Реплеи рейтинговых матчей публичны; остальные только участникам
(`Authorization: Bearer <token>`): 401 без токена, 403 чужому игроку.

Пересимуляция идёт секунды, а при нагрузке и десятки секунд (полный матч на 15 минут: около 17 с
в тёплом воркере, около 26 с с запуском воркера; воркер один, поэтому сборки идут по очереди).
Поэтому после проверки прав ответ различает три случая (#259):

| Ответ | Когда | Клиент |
|---|---|---|
| `200` и файл | кадры на диске (проверяется файл `{id}.frames.json.gz`, `replay_path` может запаздывать) | открывает реплей |
| `202` `{"status": "preparing"}`, `Retry-After: 2`, `Cache-Control: no-store` | матч ещё идёт (`matches.status = running`) или его кадры строятся (`ReplayService` помнит идущие сборки) | показывает окно «Реплей готовится» и повторяет запрос с нарастающей паузой |
| `410` | матч окончен, сборки нет, файла нет: сборка упала (хэш не сошёлся, нет места), сервер упал посреди сборки, матч прерван (`aborted`) или файл потерян | ошибка «реплей недоступен», не повторяет |
| `404` | матча с таким id нет | ошибка «не найден» |

Состояние выводится без новых столбцов БД: из `matches.status`, файла и набора идущих сборок в
памяти процесса. После падения процесса посреди сборки журнал остаётся, но заново не собирается
(это `410`).

## Структура

Один JSON-объект (gzip). Все числа целые; CP в сотых долях, прогресс ребра в тысячных (как в
`GameState`, `AGENTS.md` 4.1).

```json
{
  "format": 1, "sim_version": 1, "ruleset_hash": "...", "map_id": "arteriya", "map_hash": "...",
  "tick_hz": 10, "frame_every": 5, "ticks": 9000,
  "outcome": {"winner": 0, "reason": "vp"}, "vp": [31, 24], "state_hash": "...",
  "map": { ...формат карты, docs/design/map-format.md... },
  "frames": [ {"t": 0, ...}, {"t": 5, ...}, ... ],
  "events": [ [1, "recruit", {"node": 3, "owner": 0}], ... ]
}
```

- `outcome.winner`: `0`, `1` или `null` (ничья); `reason`: `capital`, `vp`, `forfeit` и т. д. из
  `match_ended`.
- `vp`: итоговые очки по игрокам; `ticks`: последний сыгранный тик.
- `map`: карта целиком (тот же формат, что `maps/*.json`), статика графа для рендера. Файл
  самодостаточен: правка `maps/` на него не влияет (`map_hash` для справки).
- `frames`: тик `0`, затем каждый `frame_every`-й тик (`tick_hz / 2`, то есть 2 кадра в секунду)
  и всегда последний тик матча. Время кадра в секундах: `t / tick_hz`.
- `events`: все события матча в порядке тиков, `[tick, kind, data]`; `data` плоский объект
  (`gow_sim.state.Event`). Событие тика `T` относится к состоянию «после тика `T`»: кадр
  `t = 5k` плюс события `5k < tick <= 5k + 5` описывают переход к следующему кадру.

## Кадр

| Ключ | Что | Значение |
|---|---|---|
| `t` | тик | целое |
| `p` | игроки по id (0, 1) | `[cp, vp, stance, forfeited]`: CP в сотых, `stance` строка, `forfeited` 0/1 |
| `n` | узлы по id | `[owner, warehouse, capacity]`: `owner` 0, 1 или `null`; `warehouse` зарядов на складе; `capacity` текущая ёмкость города (клиент правил не считает) |
| `w` | уровень дорог по id (имя ширины осталось с формата карты, DEC-22: 1..3) | целое |
| `g` | группы, по возрастанию `id` | объект группы (ниже) |
| `k` | пакеты зарядов, по `id` | `[id, owner, edge, from_node, charges, depart_tick, arrive_tick]` |
| `i` | публичные намерения, по `id` | `[id, owner, kind, origin, target]`, `target` может быть `null` |
| `b` | стройки дорог городами (DEC-16), по id узла; ключа нет, пока ни один город не строит | `[node, edge, done_tick]`: город, ребро, тик повышения уровня |
| `r` | тип дорог по id ребра (DEC-22); ключа нет, пока ни у одной дороги нет типа (и в файлах до DEC-22); DEC-26 [принято]: типа дорог не будет, ключ исчезнет при реализации (версию формата и чтение старых файлов решает реализация) | `none`, `fast` или `freight` |

Группа: `{"id", "o": owner, "u": units, "c": charged, "m": mode, ...}`, плюс

- `"at": node`, если группа стоит в узле; или `"on": [edge, from_node, progress, back]`, если идёт
  по ребру (`progress` 0..1000 от `from_node`, `back` 0/1: отскок назад, DEC-07);
- `"to": [node, ...]`: оставшийся путь приказа (первый элемент следующий узел), если приказ есть;
  `"pl": 1`: приказ плановый.

До DEC-16 (`sim_version` 2) у группы был ключ `"b": edge` (группа строит дорогу) и режим `build`;
просмотрщик принимает старые файлы и показывает такую группу в режиме `attack`.

`mode`: `attack`, `defense`. Узлы и рёбра идут в порядке id карты (`n[i]` это узел `i`).
Ключи, которых нет в таблице (например, память тумана `vision_memory`), в файл не попадают.

## Размер

Бюджет `AGENTS.md` 12: ≤ 2 МБ на полный матч в 15 минут (DEC-22, 1801 кадр). Измерено: матч
9000 тиков на `pautina`, боты rusher и reactive: около 65 КБ (12 минут: около 60 КБ). Дельты поэтому не нужны; если формат вырастет
(больше узлов, больше групп), тест `apps/server/tests/test_replays.py` покажет это раньше релиза.

## Просмотр в клиенте

`apps/client/src/replay/`: `replayFile.ts` (разбор и проверка `format`), `timeline.ts` (кадр в
`SnapshotMsg` с полным раскрытием; владельцы групп и пакетов отдельными таблицами),
`replayPlayer.ts` (`RenderSource`: пауза, ×1/×4/×16, перемотка, интерполяция CLI-02),
`ReplayViewer.svelte` (управление). Адрес: `/?replay=<id матча>` (`replayUrl`), в dev-сборке
`/?replay=dev` играет образец `siege.frames.json`.

Загрузка: `loadReplayWhenReady` (`loadReplay.ts`) повторяет запрос, пока сервер отвечает `202`
(паузы 2 с, 3 с, 4,5 с, затем 5 с; не дольше 5 минут, потом ошибка «слишком долго»), а
`ReplayScreen` показывает окно «Реплей готовится». `404`, `410`, `401`/`403` останавливают
ожидание сразу, у каждого своё сообщение. «Назад» возвращает на экран, с которого реплей открыт
(экран результата: `AppState.openReplay` / `closeReplay`); у прямой ссылки `/?replay=<id>` «Назад»
ведёт на `/`, а токен сохранённого гостя берётся из `localStorage`, поэтому игрок открывает
реплей своего приватного матча или матча с ботом.

## Изменение формата

Любая несовместимая правка: новый `format`, и сервер умеет писать только текущий. Старые файлы на
диске остаются; клиент просмотра поддерживает версии, которые встречаются в `data/replays/`.
