1. One visual language for both indicators

Both indicators answer the same question, how much of a thing is done, so every variant uses one grammar: one cell = one whole unit of the thing (one CP; one queued unit; one building), and a cell is in one of a few states told by a pattern or shape, never by colour alone: empty = frame only, queued = frame with a dot (a unit waits its turn), in progress = hatched and growing, done = solid, alert (CP at the cap and burning, a ready unit with no room) = amber dashed outline, pulsing, plus a word or a mark where there is room. A horizontal cell or bar is for points and time (CP, recruit, build); a square stays the charge (ui-style.md, section 21) so the two never mix. Now is the current client look (TopBar.svelte, cityView.ts), drawn from the same constants. The scale and the grayscale switches apply to the whole page.

2. The CP bar (top bar of the HUD)

The CP bar lives in the HTML HUD (Svelte), not on the map, so it costs no map FPS. Values are hundredths of CP as in the protocol; cap 5 CP (rulesets/mvp-1.toml, cp.cap = 500). A whole cell per CP; the partial cell shows regeneration. At the cap the excess burns (DEC-02). Today the "at the cap" state is told by an amber number only: colour alone (AGENTS.md, 7.4).

3. Unit recruitment and barracks construction (at a city on the map)

The recruit queue (DEC-25): up to 3 units (recruit.queue_max), 3 s per unit (recruit.unit_ticks = 30), the first unit fills, a ready unit with no room waits (recruit_waiting). The barracks build (DEC-26): city_upgrades.barracks_ticks = 100 (10 s) for 3 CP; while it is being built the city cannot recruit. A warehouse upgrade uses the same build slot but a barracks city may recruit meanwhile, so the last row shows both together. Free queue slots are drawn only for the selected city (otherwise an empty queue shows nothing). Every sample sits on a dark plate on the terrain colour chosen above.
